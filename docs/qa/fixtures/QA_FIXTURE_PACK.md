# QA Fixture Pack — synthetic ONC/RCE deliveries

**SYNTHETIC / NOT GOVERNMENT DATA. Never contains real NPIs, names, or addresses.**

Generated by `scripts/qa_fixture_pack.py`. One pipe-delimited delivery file per
scenario, each with the locked 41-column ONC/RCE header, plus `MANIFEST.json`
naming every file's sha256, row count, expected rule codes and the workflow
state it is meant to drive. Expectations were derived from rule set **1.3.0**
(`app/tefca_registry/rce/quality_rules.py`) and are checked against the live
rule functions by `tests/test_qa_fixture_pack.py`.

The generator writes files only. It opens no database session and no network
connection; registering the files on DEV is a human step described below.

## Generating

```
python scripts/qa_fixture_pack.py                      # all scenarios -> qa-fixtures/out/
python scripts/qa_fixture_pack.py --out <dir>          # elsewhere
python scripts/qa_fixture_pack.py --scale 2000         # smaller SEPTEMBER_SCALE
python scripts/qa_fixture_pack.py --only CLEAN_B1,LUHN_INVALID_NPI
python scripts/qa_fixture_pack.py --list               # names only, writes nothing
```

* Deterministic: same `--scale` produces byte-identical files and manifest
  (no randomness, no timestamps). `--only` writes a manifest that lists only
  the selected scenarios.
* Refuses to run with `ENVIRONMENT=production`, mirroring
  `scripts/seed_qa_test_data.py`.
* `qa-fixtures/out/` is git-ignored; regenerate rather than commit.
* Generation time for the default 25,000-row scale file is well under a
  second on a laptop.

## File facts

| Property | Value |
|---|---|
| Delimiter | `\|` (declare `delimiter=pipe` on upload) |
| Encoding / terminator | UTF-8, no BOM, CRLF (as the profiled delivery) |
| Header | the locked 41 columns, verbatim order |
| Filename | `SYNTHETIC-QA-<SCENARIO>.psv` |
| `id` | `9.99.777.QA<TAG>.<n>` — the first arc of any real OID is 0, 1 or 2 |
| Names | always contain `SYNTHETIC` |
| NPIs | `9xxxxxxxx` + CMS check digit (Luhn over `80840`+base); CMS only assigns NPIs starting 1 or 2 |
| Address | `1 Synthetic Way, Testville, AK 99999, USA` |
| HCID / TEFCAID | `urn:oid:<id>` / `SYN-<TAG>-TEFCAID-<n>` |
| Contacts | `SYNTHETIC CONTACT <n>`, `(555) 010-01xx`, `@example.invalid` |

## Design decisions you should know before reading results

1. **The QHIN row is always HELD.** Each file delivers its QHIN as a row
   (`sequoiaorgtype=QHIN`, `partOf` empty) so the members' `partOf` and
   `orgManagingOrg` resolve inside the synthetic arc. Rule set 1.3.0 accepts
   only Participant/Subparticipant (`REQ-001 UNKNOWN_SEQUOIA_ORG_TYPE`, HIGH,
   HUMAN_REQUIRED) and requires `partOf` (`INT-002 MISSING_PART_OF`, HIGH,
   NO_CORRECTION), because in a real delivery the QHIN is an external referent
   that promotion synthesises from `orgManagingOrg`. Leave the hold in place:
   promotion still creates the QHIN entity (`QHIN 9.99.777.QA<TAG>.1`) and the
   members attach to it. Consequently **no file reaches "Completed — Clean" on
   its own**; CLEAN_B1's member rows are clean, and "Clean" is reached by
   dispositioning the QHIN row's REQ-001 finding (a useful QA path in itself).
2. **State is AK, not MA.** `FMT-003` allocates ZIP prefix 999 to Alaska; "MA
   99999" would raise `ZIP_STATE_MISMATCH` (MEDIUM, HUMAN_REQUIRED) on every
   row.
3. **ACT-001 is conditional.** `INACTIVE_NEW_ENTRANT` fires only when the
   environment already holds an earlier delivery (`quality_engine` derives
   `new_entrant_ids` from the previous intake). On a fresh database the first
   registration is a baseline and only `CON-003 INACTIVE_RECORD` appears.
   Register INACTIVE_NEW_ENTRANT once per environment.
4. **Every file raises `SCH-002 COLUMN_EMPTY_IN_DELIVERY` once** (dataset-level,
   INFORMATIONAL) for transaction/NAIC/CCN/contact_company, as the real
   delivery does.
5. **Synthetic NPIs do not exist in NPPES.** If automated verification runs,
   expect `NPI-005 NPI_NOT_FOUND` (MEDIUM, HUMAN_REQUIRED) or `NPI-009` when the
   source is unavailable. That is verification-time behaviour, not a defect.
6. **Rows named `... TEST ORG ...`** (scale mix only) match the test-artefact
   pattern and promote with `is_test_record=true`; they are excluded from
   promotion only if `RCE_EXCLUDE_TEST_RECORDS` is set.

(`scenarios.<NAME>.expected_by_line`, keyed by line number, with
`ids_by_line` beside it). `finding_catalog` lists severity and authority for
every code the pack provokes.

## Registering on DEV (instructions only — the script never does this)

Endpoint: `POST /api/tefca/rce/official-deliveries` (multipart), role
`program_manager` or `admin` (`DATA_OPERATIONS_ROLE`). Returns HTTP 202 with a
receipt naming the job; processing is asynchronous.

| Form field | Value |
|---|---|
| `file` | the `.psv` file (the `.psv` extension carries no signature rule in the upload scanner; the content is scanned as text) |
| `delivery_period` | a label, e.g. `QA CLEAN_B1 2026-09` — part of the job identity |
| `source` | `SYNTHETIC-QA (not ONC/RCE)` |
| `received_date` | ISO date, e.g. `2026-09-30` — part of the job identity **and** the relationship boundary |
| `notes` | e.g. the manifest sha256 of the file |
| `delimiter` | `pipe` |

Example (bearer token from a `program_manager` login; `$BASE` is the DEV API):

```
curl -sS -X POST "$BASE/api/tefca/rce/official-deliveries" \
  -H "Authorization: Bearer $TOKEN" \
  -F "file=@qa-fixtures/out/SYNTHETIC-QA-CLEAN_B1.psv" \
  -F "delivery_period=QA CLEAN_B1 2026-09" \
  -F "source=SYNTHETIC-QA (not ONC/RCE)" \
  -F "received_date=2026-09-30" \
  -F "notes=sha256 <from MANIFEST.json>" \
  -F "delimiter=pipe"
```

Then poll `GET /api/tefca/rce/delivery-jobs/{job_id}` and read
`GET /api/tefca/rce/delivery-jobs/{job_id}/detail` (outcome, reconciliation
snapshot, review state, promotion summary) and
`GET /api/tefca/rce/deliveries/{intake_id}/issues` (the issue ledger).

**Idempotency.** The job identity is `sha256(file) + delivery_period
(trimmed, lower-cased) + received_date`. Re-posting the same triple while a
job is active or completed for it returns the existing job — a no-op, not a
second intake. To process the same file again deliberately, change the
`delivery_period` label or the `received_date`.

**Ordering for the pairs.**

* RELATIONSHIP_A then RELATIONSHIP_B, with B's `received_date` **strictly
  later** than A's (date granularity). The relationship boundary is
  `received_at.date()`; a boundary not after the current edge's
  `effective_date` is refused as `SNAPSHOT_MISMATCH` and nothing moves.
* CONFLICTING_EVIDENCE_A then CONFLICTING_EVIDENCE_B, B later. A must have
  been promoted (job SUCCEEDED) before B is registered, otherwise there is no
  registered NPI to conflict with.
* INACTIVE_NEW_ENTRANT after at least one other delivery exists in the
  environment (see design decision 3).

## Driving workflow states

These states come from actions on a registered delivery, not from file
content. The same table is in the manifest under `workflow_state_drivers`.

| State | Drive on | How |
|---|---|---|
| Reconciliation PASS | CLEAN_B1 | Register; wait for SUCCEEDED; the detail endpoint shows the persisted snapshot `passed=true`. |
| Reconciliation FAIL / missing snapshot | DUPLICATE_ID | SCH-003 makes `assert_ids_unique` refuse snapshot effects; the FAILED snapshot tip fails the "Snapshot effects completed" check. Decide both SCH-003 findings, then `POST /deliveries/{intake}/snapshot-effects/retry`. |
| Stale snapshot / changed record | RELATIONSHIP_A → B | Create an ARC review on S4's entity after A; register B later; `GET /deliveries/{B}/stale-marks` lists `PART_OF_CHANGED`. Resolve a mark and confirm the append-only RESOLVED row. |
| Snapshot rollback | RELATIONSHIP_B | `python scripts/rce_snapshot_rollback.py --intake <B> --plan`, then `--apply --actor <email> --role program_manager --reason "<why>"`. Fails closed once B is APPROVED and a later snapshot exists. |
| Snapshot approval | any SUCCEEDED delivery | `POST /deliveries/{intake}/snapshot/approve` (role `qalead`, `approval_ref`); refused for the registrant and for the system. |
| Terminal finding | LUHN_INVALID_NPI | `POST /issues/{issue}/dispositions` (role `reviewer`+) with `ACCEPT`/`REJECT` and a reason. A second decision on the same finding is refused with `TERMINAL_FINDING_MESSAGE`, and the attempt itself is audited. |
| Reopen | LUHN_INVALID_NPI | **No reopen endpoint exists at this revision.** `TERMINAL_FINDING_MESSAGE` names "the approved reopen workflow" as a separate, human-governed process; the QA case is the refusal plus its audit row. |
| Maker / checker | CONFLICTING_EVIDENCE_B (or any QA_REQUIRED finding) | `transition_issue` refuses `APPROVED` on a QA_REQUIRED finding without a `qa_actor` distinct from the reviewer; snapshot approval refuses the registrant. |
| Review-case lifecycle | MULTIPLE_HIGH | Each record opens two DQ cases of different classes; claim, determine and QA them independently; the hold is released only when every HIGH finding on the record is decided. |
| QA outcome PASS | CLEAN_B1 | Dispose the QHIN row's REQ-001 (WAIVE/ACCEPT), recompute holds, re-reconcile: outcome "Completed — Clean". |
| QA outcome FAIL | MALFORMED_NPI | Leave the four HELD records undecided: outcome stays "Completed — With Exceptions"; the exception ledger lists four IDENTITY holds. |
| Performance | SEPTEMBER_SCALE | Register the default 25,000-row file; time the stages and the list/detail endpoints. |

## Teardown — what actually applies

Be honest about this before registering anything on a shared environment:

* `scripts/cleanup_mock_data.py` deletes only `tefca_reviews` rows with
  `is_mock_data = true` (and their `tefca_findings`). **It does not touch
  anything an RCE delivery creates** — intakes, source records, issues,
  curated records, jobs, dispositions, snapshots, registry entities or DQ
  review cases. It is not a teardown for this pack.
* `scripts/cleanup_benchmark_entities.py` soft-deletes registry entities by
  TEFCAID prefix (`TID-P100-` …) through `DELETE /api/tefca/registry/entities/{id}`.
  Its prefixes do not match this pack's `SYN-<TAG>-TEFCAID-` values, so as
  written it removes nothing here; the same endpoint could soft-delete the
  synthetic entities (names contain `SYNTHETIC`, the synthesised QHIN is
  `QHIN 9.99.777.QA<TAG>.1`) if a deliberate cleanup is decided.
* Area 1 (`rce_source_intakes`, `rce_source_records`) is **append-only by
  design**; there is no delivery-deletion mechanism and none should be added
  for QA convenience. A synthetic delivery registered on DEV stays in DEV,
  identifiable by `source = "SYNTHETIC-QA (not ONC/RCE)"`, its
  `delivery_period` label and the `9.99.777.QA` arc.

Recommendation: run destructive or repeated scenarios against an isolated
database (the local PostgreSQL recipe used by the remediation sprints), and
treat a DEV registration as a deliberate act recorded in the QA log.

## Verifying the pack

```
python -m pytest tests/test_qa_fixture_pack.py -q
```

The tests generate the pack into a temporary directory and check: byte
identity across two runs; the 41-column header; every `id` in
`9.99.777.QA*` and every name containing `SYNTHETIC`; every valid NPI passes
`app.services.npi_validator.validate_npi` and every Luhn-invalid one fails;
manifest completeness; `--scale`; and — DB-free — that the project's quality
rules raise exactly the codes the manifest promises for every line of every
file, with the catalogued severity and authority.

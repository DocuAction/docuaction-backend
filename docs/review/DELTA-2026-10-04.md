## 1. Contract mapping (source: `qa-evidence/PROJECT_CONTRACT_CONTEXT.md`, found — not blocked)

The contract (Task 2, Deliverable 2) requires a COR-accepted methodology
addressing, among other things, a "discrepancy taxonomy" and handling of
"incomplete, inconsistent and variable-quality submissions" (Task 3). The
contract context file states this directly and is the authority this delta
maps against — not reconstructed from memory:

> "Do not assume all 41 directory fields can be verified by every external
> source. Track requiredness, applicability and verifiability separately per
> field." — and — "Distinguish missing evidence, unsupported checks,
> ambiguous matches and confirmed discrepancies. Do not automatically
> classify every blank field as non-compliance."

Preflight enforcement is the delivery-intake-time mechanism that keeps this
distinction intact BEFORE a record ever reaches the four-category Task 3/4
discrepancy taxonomy (no discrepancies / minor-administrative / inexplicable
/ non-compliant): a parsing or schema problem is not a discrepancy about an
entity at all, and must not be allowed to manufacture one. This delta does
not resolve the open contract questions (closeout-window wording, the full
Task 6 rights clauses, the 1,298 interpretation, the deliverable-number
mapping) — none of those are touched by this work, consistent with "keep
the 1,298 interpretation unresolved."

## 2. Existing implementation — this is substantial, and already close to
   what was asked for; the gap is enforcement, not engine design

### 2.1 The preflight engine itself (`app/tefca_registry/rce/preflight.py`,
    603 lines) is COMPLETE and well-designed for exactly this purpose

It already implements, for ONC deliveries:
- **SCHEMA** (`_schema_findings`): BOM detection, missing/extra/renamed/
  reordered columns against the locked 41-field map (`PF-SCH-001..007`),
  delimiter and encoding mismatches, mojibake detection flagged at the
  encoding level.
- **IDENTIFIER**: reuses quality rules (`SCH-003`, `ID-001/003`,
  `NPI-002/003/004`) PLUS three checks no quality rule covers
  (`PF-OID-001`, `PF-HCID-001`, `PF-CCN-001` — OID/UUID/HCID/CCN shape).
- **CONDITIONAL_BLANK**: reuses `ID-002/005`, `REQ-001/002/003`, `INT-001`,
  `CON-003`.
- **MISSING_CONTEXT**: reuses `INT-002`; plus `PF-CTX-000/001` for the
  specific NPI-requirement-cannot-be-decided case (blank NPI + blank
  hl7orgrole), explicitly recorded as `UNRESOLVED` applicability, never as
  a missing required field.
- **Four separate dimensions per finding** (`applicability`, `execution`,
  `evidence`, `disposition`) — this is the "four target dimensions, never
  one status" principle the engine already enforces, and it is the direct
  ancestor of this task's requested Applicability/Match/Execution/
  Freshness/Verification dimension set (§5 below maps the correspondence
  rather than replacing it).
- **A classification gate** (`GATE_CLEAR` / `GATE_CLEAR_WITH_FINDINGS` /
  `GATE_BLOCKED`), computed from the worst disposition seen
  (`run_preflight`, line ~495) — already distinguishes "block the whole
  delivery" from "clear, with findings a human should see" exactly along
  the lines this task asks for.
- **Originals-never-touched discipline**: derived normalizations
  (whitespace trim, the four `_NORMALIZING_RULES`) are written to
  `rce_preflight_normalization`, never back onto `rce_source_records`.
- **Shadow comparison** (`shadow_reassessment.py`, `preflight_shadow_models.py`):
  a real, working comparison against the preserved `SEED_RULES_V4`
  candidate, already proven in Round 20 against the real file (not a mock).

### 2.2 The genuine gap: `run_preflight` has exactly ONE caller in the
    entire application, and it is not in the real pipeline

```
$ grep -rn "run_preflight\b" app/ --include="*.py" | grep -v "def run_preflight"
app/tefca_registry/rce/preflight_shadow_routes.py:64:
    return await pf.run_preflight(db, iid, actor=_actor(user))
```

That one call site is `POST /deliveries/{intake_id}/preflight`
(`preflight_shadow_routes.py:57`) — an **admin-triggered, on-demand dry-run
route**. Nothing calls it automatically. Confirmed by tracing the real
pipeline, not inferred from a docstring:

- `app/tefca_registry/rce/delivery_runner.py` is "THIS MODULE IMPLEMENTS NO
  PIPELINE STAGE" by its own docstring but IS the orchestrator that runs
  the stages in order. `_run_after_area1`'s stage tuple (line ~242) is:
  `(STAGE_QUALITY, STAGE_CURATION, _stage_quality), (STAGE_CURATION,
  STAGE_PROMOTION, _stage_curation), (STAGE_PROMOTION, STAGE_VERIFICATION,
  _stage_promotion), (STAGE_VERIFICATION, STAGE_RECONCILIATION,
  _stage_verification)`. **There is no `STAGE_PREFLIGHT` entry.** Area 1
  (`_stage_area1`, ingest) runs directly into `STAGE_QUALITY`
  (`_stage_quality` → `quality_engine.run_quality_engine`) with nothing in
  between.
- `app/tefca_registry/rce/intake.py` (409 lines, `ingest_delivery` at
  line 251) contains the string `"preflight"` **zero times**.
- `app/tefca_registry/rce/delivery_job_model.py`'s `STAGE_ORDER` tuple
  (line 86) — `(STAGE_ACCEPTED, STAGE_PARSING, STAGE_QUALITY,
  STAGE_CURATION, STAGE_PROMOTION, STAGE_VERIFICATION,
  STAGE_RECONCILIATION, STAGE_READY)` — likewise has no preflight stage.
- The IQVIA reference-snapshot path (`iqvia_routes.py` →
  `_register_and_enqueue` → `iqvia_import.py`'s `_import_csv`) never calls
  `run_preflight` either, and has no comparable schema/identifier check of
  its own before staging rows into `iqvia_hco`/`iqvia_hcp`/
  `iqvia_affiliation_observation`.

**This is the actual gap this task is enforcing against: a complete,
tested, four-dimension preflight engine that no real delivery or reference
snapshot ever passes through.** It is reachable only by an admin
deliberately POSTing to a dry-run route after the fact — by which point
`STAGE_QUALITY`/`STAGE_CURATION`/`STAGE_PROMOTION` have already run over
data the engine might have flagged as `GATE_BLOCKED`.

### 2.3 Why this matters concretely (not hypothetical)

`quality_engine.run_quality_engine` (the real, always-run stage) and
`preflight.run_preflight` (the real, never-run-automatically stage) both
read `rce_source_records.parsed` and both call into the SAME
`quality_rules.RULE_BY_ID` registry — `preflight.py`'s own docstring is
explicit that it "CALLS that rule" rather than re-implementing it. So the
quality engine today evaluates every rule, including the ones preflight
would use to BLOCK, but has no concept of "block" at all — it records
`rce_issues` rows and continues into curation/promotion regardless. A
delivery with `truly_missing` 41-field columns (schema gate `PF-SCH-001`,
`disposition=DISP_BLOCKED` in preflight's own model) would today still be
curated and promoted, because nothing reads `classification_gate` before
`STAGE_CURATION` runs.

## 4. Source / field / check dependencies

- `preflight.py` imports `field_map.FIELD_BY_NAME`/`Necessity` (41-field
  map, version `FIELD_MAP_VERSION = "1.0.0"`, `field_map.py`), and
  `quality_rules.RULE_BY_ID`/`RULE_SET_VERSION = "1.3.0"`
  (`quality_rules.py`) — both versions are stamped onto every
  `RcePreflightRun` row already (`preflight.py` line ~443), so a run is
  always traceable to the exact map/rule-set versions it was evaluated
  against. No new version scheme is needed for enforcement.
- `_REUSED_RULES` (preflight.py line ~76) is the exhaustive list of which
  quality rules preflight consults and which category each lands in —
  this is the "existing equivalents" an enforcement layer must keep
  consistent with; adding a rule to `quality_rules.py` without adding it
  here (when it is schema/identifier/conditional-blank/missing-context in
  nature) would silently exclude it from preflight's gate while the
  quality engine still evaluates it. **Policy question, not resolved
  here**: should `_REUSED_RULES` membership be enforced by a test that
  fails when a new rule of a matching category is added to
  `quality_rules.ALL_RULES` without a corresponding preflight entry? Left
  open for Part B — not implemented in this round.
- `_REQUIRED`/`_CONDITIONAL` (preflight.py line ~114) are derived directly
  from `field_map.FIELD_BY_NAME`'s `Necessity` enum — not hardcoded
  separately, so a future field-map change to a field's necessity is
  picked up automatically, with no second place to update.

## 5. Existing enum-to-target-state mapping (reuse, not replacement)

The task's five conceptual dimensions are mapped onto REAL, ALREADY-USED
enums below. None of these is renamed or replaced; where no exact existing
equivalent exists, the gap is named rather than invented.

| Conceptual target | Existing equivalent | Where | Notes |
|---|---|---|---|
| **Applicability**: APPLIES / NOT_APPLICABLE / UNRESOLVED | `preflight_shadow_models.APPLICABILITY = (APPLIES, DOES_NOT_APPLY, UNRESOLVED)` | `preflight_shadow_models.py:47-50` | Exact match except casing (`"applies"` lowercase vs. the task's uppercase convention) and `DOES_NOT_APPLY` vs. `NOT_APPLICABLE` — same concept, existing spelling kept, not renamed. |
| **Match**: MATCHED / NO_MATCH / AMBIGUOUS | `snapshot_models.MATCH_CANDIDATE`, `MATCH_EXCEPTION`, `MATCH_AUTO_APPROVED`, `MATCH_QA_APPROVED`, `MATCH_ANALYST_APPROVED` | `snapshot_models.py`, consumed by `source_matching.py` | Richer than a 3-state enum by design (it separately tracks WHO approved a match, which the task's 3-state model does not need to reproduce). No new enum needed; a reporting view can project the 5 states down to 3 if a 3-state summary is ever required, but the underlying 5-state model should not be collapsed in storage. |
| **Execution**: DONE / UNAVAILABLE / HELD / INSUFFICIENT | `preflight_shadow_models.EXECUTION = (EXEC_DONE, EXEC_UNAVAILABLE, EXEC_INSUFFICIENT)` | `preflight_shadow_models.py:53-56` | Three of the four task states exist exactly. **`HELD` has no existing equivalent in this enum** — it is a genuine gap, not a renaming. | **Freshness**: CURRENT / STALE / UNKNOWN | `snapshot_models.STALE_PART_OF_CHANGED`, `STALE_QHIN_CHANGED`, `STALE_ACTIVE_CHANGED`, `STALE_PURPOSES_CHANGED`, `STALE_NPI_CHANGED`, `STALE_CCN_EVIDENCE_CHANGED`, `STALE_SANCTION_CHANGED`, `STALE_MATCH_CHANGED`, `STALE_ABSENT_FROM_DELIVERY` (9 reason-coded staleness causes) | `snapshot_models.py:58-66`, consumed by `delivery_delta.py` | Richer than CURRENT/STALE/UNKNOWN: it already names WHY something is stale, which the task's 3-state model would flatten. The existing `supersedes_snapshot_id`/`supersedes_relationship_id`/`supersedes_match_id` FK-chain (same file) is the CURRENT-vs-superseded mechanism — a row with nothing superseding it is CURRENT; the 9 `STALE_*` reasons are sub-states of STALE; UNKNOWN has no existing equivalent and is a genuine gap (see §6). |
| **Verification**: VERIFIED / MISMATCH / NOT_VERIFIABLE / UNSUPPORTED / NOT_EVALUATED | `verification_findings.OUTCOMES = (VERIFIED, NPI_NOT_FOUND, NPI_DEACTIVATED, NPI_VERIFICATION_UNAVAILABLE)` | `verification_findings.py:49-53` | `VERIFIED` is exact. `NPI_NOT_FOUND`/`NPI_DEACTIVATED` together are domain-specific refinements of MISMATCH (more precise, not a renaming target). `NPI_VERIFICATION_UNAVAILABLE` ≈ NOT_VERIFIABLE/UNSUPPORTED collapsed into one value today — the task's distinction between "the check exists but nothing answered" (NOT_VERIFIABLE) and "no check exists for this at all" (UNSUPPORTED) is NOT currently separated here. | **Disposition** | `preflight_shadow_models.DISPOSITION = (DISP_OPEN, DISP_INFORMATIONAL, DISP_BLOCKED)` | `preflight_shadow_models.py:59-62` | Already exists, already governs the classification gate (§2.1). Task explicitly says to preserve existing governed workflow states here — done, nothing changed. |

**Net assessment**: four of five dimensions already have a working,
real equivalent; the fifth (Match) is intentionally richer than requested.
The one concrete, scoped addition this delta recommends is `EXEC_HELD`
on the existing `EXECUTION` tuple (additive, non-breaking) — needed to
represent "the check could not run because the delivery/record is
held pending resolution," which is distinct from `EXEC_UNAVAILABLE`
("no check exists") and `EXEC_INSUFFICIENT` ("inputs this delivery does
not carry"). `UNKNOWN` (Freshness) and the NOT_VERIFIABLE/UNSUPPORTED
split (Verification) are named as open gaps, explicitly NOT implemented
in Part A — each would require tracing every existing call site that
currently uses the coarser value, which is Part B/C scope, not something
to rush into this round's commit.

## 6. Policy questions and authority references (not resolved here)

1. **Should `GATE_BLOCKED` block the whole delivery, or only the affected
   records?** The task's own instruction (§3) says: "Block an entire
   delivery only when parsing, completeness or identity cannot be
   trusted. Otherwise hold affected records, sources or checks." The
   existing `run_preflight` already computes a single delivery-level
   `classification_gate` from the WORST finding — this is consistent with
   "block only when untrustworthy" IF AND ONLY IF the only findings that
   produce `DISP_BLOCKED` today are schema-level (`PF-SCH-001`, missing
   columns) — confirmed true by reading `_disposition_for`/`_schema_findings`:
   every per-record finding's disposition comes from `_disposition_for`,
   which only ever returns `DISP_OPEN` or `DISP_INFORMATIONAL`, never
   `DISP_BLOCKED` — **only the delivery-level schema check
   (`PF-SCH-001`) can produce `DISP_BLOCKED` today.** This means the
   existing gate computation ALREADY matches the task's intended
   semantics (whole-delivery block only for untrustworthy parsing/schema;
   everything else surfaces as an open finding, i.e., effectively a hold
   on the record, not the delivery) — confirmed by code reading, not
   assumed. No change needed to the gate's blocking criteria; this is a
   case where the existing design already matches policy, not a gap.
2. **Should reference-snapshot (IQVIA) preflight reuse the SAME
   `preflight.py` engine, parameterized by a different field map, or is a
   separate engine warranted?** IQVIA's own field shapes (HCO/HCP/
   affiliation CSVs) are structurally different from the RCE 41-field
   map — `preflight.py`'s `_schema_findings` is hardcoded against
   `field_map.RCE_FIELDS`. Reusing it as-is would require either (a)
   parameterizing `_schema_findings` by an injected field list (a real,
   scoped code change), or (b) writing IQVIA-specific schema/identifier
   checks that call the SAME shared helpers (`_CCN_RE`, OID/UUID
   validators) rather than duplicating logic. **Not decided in this
   delta** — Part A's scope is the ONC delivery path, which already has a
   complete engine; the IQVIA parameterization is flagged as Part B scope
   per the task's own "Remaining work for Part B" requirement, not
   implemented this round to avoid a rushed, under-tested field-map
   abstraction.
3. **Authority for the "block entire delivery" threshold**: this delta
   relies on the contract context's own language ("Distinguish missing
   evidence, unsupported checks, ambiguous matches and confirmed
   discrepancies") as the authority for keeping delivery-level blocks
   narrow (schema-untrustworthy only) and everything else scoped to the
   record/field level — not a new policy invented for this task.

## 7. Prioritized implementation and tests (this round's actual scope)

**P0 (this round)**: Wire `run_preflight` into the real ONC delivery
pipeline as a new `STAGE_PREFLIGHT`, gated by a new, default-OFF feature
flag (`ENABLE_PREFLIGHT_ENFORCEMENT`, same `getattr(settings, ...)` /
`os.environ` pattern as `source_matching.LICENSED_SOURCE_FLAG`), inserted
between `_stage_area1` and `_stage_quality`. When the flag is off
(default, unchanged behavior for official writes), the stage records an
informational, non-blocking entry and the pipeline proceeds exactly as
today — zero behavior change for any existing official delivery. When on
(disposable-environment testing only, this round), a `GATE_BLOCKED` result
fails the job at the PREFLIGHT stage with the existing
`stage_events`/`finish_failed` mechanism (same pattern Area 1 already
uses), and `GATE_CLEAR_WITH_FINDINGS` proceeds while the findings remain
queryable via the existing `preflight_shadow_routes` GET endpoints — no
new "hold" storage mechanism is invented, since `DISP_OPEN` findings on
real records already ARE the hold mechanism (confirmed in §6.1: no
per-record finding reaches `DISP_BLOCKED` today).

**P1 (this round)**: add `EXEC_HELD` to `preflight_shadow_models.EXECUTION`
(additive). Not yet wired to any new code path — recorded as available
for Part B's record-level hold semantics, not force-fit into Part A's
delivery-level gate.

**P2 (deferred to Part B, named not implemented)**: IQVIA reference-
snapshot preflight parameterization (§6.2); the NOT_VERIFIABLE/UNSUPPORTED
split for Verification; the UNKNOWN Freshness state; the `_REUSED_RULES`
consistency test (§4).

**Tests (this round)**: synthetic fixture corpus under
`tests/fixtures/seeded/` (manifest-driven) exercising the flag ON path
against disposable databases only; targeted unit coverage for the new
`STAGE_PREFLIGHT` stage function and the flag's off/on behavior. Full
detail and results: `REVIEW-PACKAGE-PREFLIGHT-A-2026-10-04.md` (written
after implementation, per the task's own ordering).
